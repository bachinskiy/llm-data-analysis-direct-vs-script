# Фактичні умови та правила перевірки

## Рядковий контракт

Вхід: `raw_id`, `report_year`, `track_type`, `damage_text`, `injured_text`, `hazmat_released_text`. Вихід: `raw_id,report_year,track_type,severity_class,valid_damage_usd,valid_injured,valid_hazmat`. Порядок і кількість записів зберігаються.

Контрольна реалізація B/C приймає для збитків `0`, ціле число без початкового нуля або число з правильно згрупованими тисячами. Її точний шаблон:

```text
^(?:0|[1-9][0-9]*|[1-9][0-9]{0,2}(?:,[0-9]{3})+)$
```

Для кількості травмованих та вагонів із витоком небезпечних речовин приймається непорожня послідовність ASCII-цифр. Невалідне поле перетворюється на null. Порожній числовий CSV-осередок позначає null. Числа з розділювачами тисяч у взятому в лапки CSV-осередку перевіряються за числовим значенням; це перевірка значень, а не однаковості текстового оформлення CSV.

Пріоритет правил класу: якщо хоча б одне числове поле невалідне, `unknown`; інакше травмованих > 0, вагонів із витоком > 0 або збитки >= 1 000 000 дають `critical`; далі збитки >= 100 000 дають `high`, >= 10 000 дають `medium`, решта `low`. Це умовні класи експерименту, а не нормативна шкала FRA.

В оригінальних природномовних інструкціях вживалося слово «digits», яке не повністю визначає поведінку для початкових нулів. Окремі згенеровані програми приймають такі значення ширше за контрольну реалізацію. У перевірених масивах це не змінило результату. Збережений код не виправляли заднім числом. Додатковий тест синтетичних граничних випадків, коли він наявний, є післяекспериментальним аудитом і не входить до usage модельних виконань.

## Фактичні траєкторії

| Історична умова | Що зафіксовано |
|---|---|
| M2 Direct, 3 виконання | PowerShell-перетворення, читання результату інструмента, повернення 1 000 рядків у фінальному CSV моделі |
| M3 Direct, 3 виконання | PowerShell-перетворення принаймні частини рядків, повернення повного CSV моделі |
| M4 Direct, 3 включені виконання | Вхід із 1 000 рядків, без інструментів, модельний JSON; детерміноване збереження в CSV |
| M2/M3/M4 Script, по 3 виконання | Генерація `transform(rows)` без читання вихідних записів; зовнішній запуск над зафіксованим входом |
| C, по 1 виконанню M2/M3/M4 | Генерація програми; зовнішнє застосування до всіх 215 849 записів |

Отже, лише M4 у B безпосередньо зіставляє модельне перетворення без інструментів із програмним. Для M2/M3 B дозволяє зіставляти витрати повернення великого рядкового результату через модель і витрати генерації окремо виконуваної програми. Файлові назви `direct` збережено для зв'язку з первинними даними.

M2 запускався в окремих чатах Codex Desktop; метадані журналів містять `0.158.0-alpha.2.1`. M3 запускався через `codex exec` з read-only sandbox і новою сесією. Доступна версія виконуваного CLI для кожного M3-запуску окремо не зафіксована, її не виведено з поточного встановлення. M4 використовував Responses API, `background: true`, `max_output_tokens: 128000`, структурований вихід; збережені `request_settings.json` показують фактичні параметри кожного звернення. Повернутий API ідентифікатор моделі збігається із заявленим.

У Script контракт вимагав `{records, summary}`, але структура summary не була повністю уніфікована. Перевіряються лише сім полів records; usage включає увесь згенерований код. В усіх C-моделей були текстові правила, але заявлену у старому плані передачу окремого edge-case fixture первинні постановки не підтверджують.

## Облік

Суми M2 отримано додаванням `usage` окремих `token_usage_record`, а не накопичувальних `turn_token_usage`. M3 використовує `turn.completed.usage`, M4 використовує `response.usage`. Записи міркування вже входять у вихідні токени.

```text
USD = [2*(input-cache_read-cache_write) + 0.2*cache_read
       + 2.5*cache_write + 12*output] / 1 000 000
```

`no_cache_usd = (2*input + 12*output)/1 000 000` є арифметичним аналізом чутливості. Час не використовується для порівняння: первинні межі вимірювання різні, частина журналів має файлові часові позначки, які не відображають тривалість обчислення.

Пакет містить відібрані успішні результати. У `not_in_summary.json` збережено облік відомих невключених спроб. Він не є повним журналом усіх історичних витрат і не дозволяє оцінити ймовірність успіху з першої спроби.
